# Обучалка Сашки вайбкодингу

Как писать промпт агенту в этом проекте, чтобы получилось с первого раза.

## Главное правило

**Описывай ЧТО нужно пользователю, а не КАК это писать.**

Все правила — стек, структура папок, цвета, переводы, кэш, проверка кода — уже
лежат в `frontend/.claude/skills/`. Агент подхватывает их сам. Твоя задача —
объяснить задачу, а не архитектуру.

```
❌ Создай компонент LikesPage.tsx в pages, используй Tailwind и react-query,
   не забудь про типы и локализацию

✅ Добавь экран «Мои симпатии»: список тех, кто меня лайкнул,
   с кнопками «Ответить» и «Пропустить»
```

Первый вариант хуже: ты потратил время, ограничил агента своими догадками
о структуре и всё равно ничего нового ему не сказал.

## Скелет промпта

Четыре строки, любую можно опустить, если нечего сказать:

```
1. Что сделать и что видит пользователь
2. Где это живёт (адрес экрана, какой экран правим)
3. Откуда данные
4. Чего НЕ делать в этой задаче
```

Пример целиком:

```
Добавь экран «Мои симпатии» по адресу /likes.
Список тех, кто меня лайкнул: фото, имя, возраст, кнопки «Ответить» и «Пропустить».
Данные посмотри в backend/, чего нет — заглушкой.
Оплату зорками и анимации пока не делай.
```

## Что агент делает сам, без напоминаний

Это писать в промпте не нужно:

| Само собой                                            | Почему                  |
| ----------------------------------------------------- | ----------------------- |
| Кладёт файлы в правильные папки                       | скилл `fe-architecture` |
| Верстает на токенах темы, работает в светлой и тёмной | скилл `fe-styles`       |
| Выносит тексты в переводы (ru/be/en)                  | скилл `fe-i18n`         |
| Делает загрузку, пустое состояние и ошибку            | скилл `fe-component`    |
| Настраивает кэш и инвалидацию запросов                | скилл `fe-data`         |
| Ставит заглушку, если эндпоинта нет                   | скилл `fe-api-contract` |
| Переиспользует готовые хуки и компоненты              | скилл `fe-code-style`   |
| Прогоняет `npm run check` перед сдачей                | скилл `fe-done-check`   |

Если написать «не забудь про типы и линтер» — ничего не сломается, но это шум.
Лучше этими же словами сказать что-то полезное про задачу.

## Примеры по типам задач

### Новая страница

```
Добавь экран профиля по адресу /profile: фото, имя, возраст, город, «О себе»,
кнопка «Редактировать». Данные — из backend/.
```

### Маленькая правка

```
На главном экране кнопка «Продолжить» должна быть неактивной, пока не загрузился баланс.
```

### Баг

Опиши три вещи: что сделал, что ожидал, что получилось.

```
Открываю /likes, жму «Ответить» — счётчик симпатий не уменьшается,
хотя запрос уходит успешно. Должен уменьшаться сразу.
```

Не пиши «пофикси баг с лайками» — агент начнёт угадывать.

### Стили разъехались

```
Приведи экран онбординга к общему виду: отступы и размеры кнопок как на главной.
```

### Что-то тормозит

```
Лента дёргается при свайпе на телефоне. Разберись почему и починь.
```

### Большая фича, непонятно с чего начать

```
Хочу мини-игру «20 дилемм» для мэтчей. Разберись, что именно нужно,
и предложи план.
```

Дальше агент проведёт тебя по шагам сам (см. ниже).

## Когда задача большая

Если это не правка, а целая фича на несколько экранов — не пиши всё одним
промптом. Есть процесс BMAD, шесть коротких фраз, каждая в своём сообщении:

```
1. Хочу <фича>. Разберись, что нужно, и составь бриф.
2. Бриф ок. Разбей на истории с критериями приёмки.
3. Спроектируй техническое решение.
4. Подготовь первую историю к работе.
5. Возьми историю 3.1 и реализуй её.       ← лучше в новом чате
6. Проверь историю 3.1.
```

Зачем: агент пишет план в файлы (`docs/prd.md`, `docs/stories/`), и на шаге 5
ему уже не нужна вся переписка — он читает одну историю. Меньше контекста,
меньше ошибок.

Правило простое: **одна история — один чат**.

## Как принимать работу

Агент обязан в конце сказать: что сделал, какие файлы, что осталось, какие
заглушки поставил. Если этого нет — спроси:

```
Что именно проверил? npm run check прогонял?
```

Полезно попросить показать результат глазами:

```
Запусти приложение и покажи экран.
```

Не принимай «готово» без ответа на «что проверено».

## Плохо → хорошо

| Плохо                                                 | Почему плохо          | Хорошо                                                                                |
| ----------------------------------------------------- | --------------------- | ------------------------------------------------------------------------------------- |
| «Сделай красиво»                                      | нечего проверить      | «Увеличь отступы между карточками до как на главной»                                  |
| «Добавь лайки»                                        | непонятен объём       | «На карточке ленты кнопка «Нравится» отправляет лайк и показывает следующую карточку» |
| «Почини»                                              | нет симптома          | «При открытии /matches пустой экран вместо списка, в консоли ошибка 401»              |
| «Отрефактори проект»                                  | бесконечная задача    | «Убери хардкод цветов на экране онбординга»                                           |
| «Сделай страницу, компонент, хук и стор для симпатий» | это план, а не задача | «Добавь экран «Мои симпатии» по адресу /likes»                                        |

## Частые ошибки

**Смешивать несколько задач в одном промпте.** «Добавь экран симпатий, ещё
поправь кнопку на главной и обнови цвета» — получишь три посредственных
результата вместо одного хорошего. По одной задаче.

**Ссылаться на «то, что мы обсуждали выше» в новом чате.** Агент не видит
прошлых чатов. Всё важное либо в промпте, либо уже в файлах проекта.

**Просить менять `backend/`.** Это другой пакет со своими правилами. Фронт
оттуда только читает контракт API.

**Спорить с правилами в промпте.** «Положи это в отдельную папку utils» —
агент так не сделает, потому что правила говорят иначе, и вы потратите время.
Если правило мешает — скажи об этом прямо: «правило про X мешает, обсудим?»
Правила лежат в файлах и меняются, но осознанно, а не по ходу задачи.

**Ждать угадывания.** Если в задаче есть развилка (что показывать при пустом
списке, сколько стоит действие) — либо скажи, либо разреши решить самому:
«детали на твоё усмотрение».

## Шпаргалка

```
Что сделать:  <что видит и делает пользователь>
Где:          <адрес экрана или какой экран правим>
Данные:       <откуда; или «посмотри в backend/»>
Не надо:      <что вне задачи>
```

Всё остальное агент знает. Если сомневаешься — пиши короче: лишнее он спросит сам.
