# Как работать против реального бэкенда

Задеплоенный API: `https://api-production-3ead.up.railway.app`
Проверено 25.08.2026: `/api/health` — `Healthy`, `/openapi/v1.json` — 27 эндпоинтов.

## Что мешает просто открыть его в браузере

Сам API из браузера доступен. Упирается ровно одно место — вход.

`POST /api/auth/telegram` проверяет `initData`
(`backend/src/Blizka.App/Telegram/TelegramInitDataValidator.cs`):

1. HMAC-SHA256-подпись строки по токену бота;
2. свежесть `auth_date` — не старше 5 минут.

Без подписи сервер отвечает `401 TELEGRAM_INIT_DATA_INVALID`, а остальные
эндпоинты требуют `Bearer` и тоже отдают 401.

Постоянного обхода в бэкенде по-прежнему нет — `backend/docs/dev/telegram-test-auth.md`
актуален для входа под настоящим Telegram-id (см. Вариант 1). Но появился
**временный** demo-режим для ручного тестирования без токена бота вообще —
см. Вариант 3 ниже.

Второе — CORS. Заголовки приходят только для `https://web.telegram.org`;
с любого другого origin preflight возвращает 204 без `Access-Control-Allow-Origin`.
Поэтому `VITE_API_BASE_URL` оставляем пустым и ходим через dev-прокси Vite:
он серверный, для браузера это тот же origin, и CORS не участвует.

## Вариант 1: браузер (нужен токен бота)

Это **настоящий вход**, а не тестовый режим. Dev-сервер подписывает initData
токеном бота — плагин `vite/dev-telegram-auth.ts`, тот же алгоритм, что в
`backend/scripts/generate-telegram-init-data.js`. Подпись подлинная, поэтому
бэкенд опознаёт ровно того пользователя, чей Telegram-id стоит в панели
разработки: тот же аккаунт, те же данные, что и при запуске из Telegram.
Бэкенд при этом не ослабляется и не знает про этот путь.

Подменяется только оболочка клиента — тема, вьюпорт, хаптика. Поле `user`
плагин берёт из браузера как есть и не трогает.

1. В `.env` (файл не в репозитории):

   ```
   VITE_API_BASE_URL=
   VITE_API_PROXY_TARGET=https://api-production-3ead.up.railway.app
   VITE_MOCK_TELEGRAM=1
   TELEGRAM_BOT_TOKEN=<токен того же бота, что настроен на стенде>
   DEV_USER_ID=<свой Telegram-id, подскажет @userinfobot>
   DEV_USER_NAME=<имя>
   DEV_USER_USERNAME=<юзернейм без @>
   ```

   `DEV_USER_*` — без префикса `VITE_` намеренно: с ним Vite вшил бы личный
   Telegram-id в production-бандл (проверено — вшивал). Значение подставляет
   плагин `vite/dev-user-define.ts` — он работает и на `vite build` (не только
   на dev-сервере), это нужно для задеплоенного dev-стенда фронта, см. ниже.

   Токен берётся из переменной `Telegram__BotToken` в Railway. Он без префикса
   `VITE_`, поэтому в бандл не попадает и в браузер не уходит. Никуда, кроме
   локального вычисления подписи, не передаётся.

2. `npm run dev` — в логе появится строка про подпись initData.

3. Открыть `http://localhost:5173`. Вход пройдёт как у обычного пользователя:
   `user.id` из плагина станет `TelegramId` в БД.

Пустой `TELEGRAM_BOT_TOKEN` — вход вернёт 401, и экран загрузки покажет
«Не удалось войти» с кнопкой повтора. Это ожидаемо, а не поломка.

Плагин работает только при `VITE_MOCK_TELEGRAM=1`: внутри настоящего клиента
подменять initData нельзя — там приходит подпись реального пользователя.

## Вариант 2: внутри Telegram (токен не нужен)

1. В `.env`: `VITE_MOCK_TELEGRAM=0`, `VITE_API_PROXY_TARGET` — адрес стенда.
2. `npm run dev:https` и туннель до порта 5173 (cloudflared, ngrok — любой).
   Telegram грузит Mini App только с публичного https-адреса.
3. В BotFather указать этот адрес как Mini App URL и открыть бота.

Клиент подставит подлинный initData, плагин в это не вмешивается.

## Вариант 3: демо-пользователи (без токена бота, ВРЕМЕННО)

Отдельный, временный путь тестирования — специально для того, чтобы не
проходить онбординг заново на каждом прогоне. Бэкенд (спека 003,
`backend/docs/specs/003-demo-seed-data.md`) держит 10 фиксированных
демо-аккаунтов с готовыми анкетами, фото, мэтчами и лайками, и умеет выдавать
JWT для любого из них в обход `initData` — по общему секрету, а не по
Telegram-подписи. Секрет живёт в Railway (`DevLogin__Secret`) и пуст по
умолчанию: пока он не задан явно, эта дверь закрыта и от обычного `initData`-входа
ничего не меняется.

**Это не полноценная авторизация и не постоянная фича** — «дверь для одного
доверенного человека» на время ручного тестирования на проде, пока нет
staging-окружения. Как перестанет быть нужно — секрет на Railway снимается
(возвращается к пустому), и весь demo-путь на бэкенде и фронте отключается
сам, без правок кода.

1. В `.env`: тот же `VITE_MOCK_TELEGRAM=1`, что и в Варианте 1, плюс
   `DEV_LOGIN_SECRET=<секрет с Railway>`. `TELEGRAM_BOT_TOKEN` не нужен —
   можно оставить пустым.

   Секрет без префикса `VITE_` намеренно, как и `TELEGRAM_BOT_TOKEN`: значение
   подставляется dev-сервером (`vite/dev-login-auth.ts`) на пути к прокси и в
   браузер не уходит. Пока `DEV_LOGIN_SECRET` задан, он выключает подпись из
   Варианта 1 (`vite/dev-telegram-auth.ts` в этом режиме молчит) — оба пути
   одновременно не работают, это осознанно: смешивать подписанный initData и
   demo-заголовки бэкенду незачем.

2. `npm run dev` — в логе появится строка про demo-вход.

3. В панели разработки (иконка справа сверху) в поле **Telegram-id** вписать id
   демо-аккаунта — подходят только `990000000001`–`990000000010` — и нажать
   «Войти этим пользователем». Из интерфейса демо-данные больше не пересидировать:
   кнопку убрали, эндпоинт `POST /api/dev/reseed-demo-data` на бэкенде остался.

Есть ограничение, которого нет в Варианте 1: войти можно только под одним из
этих 10 `TelegramId` (`990000000001`–`990000000010`). Свой настоящий Telegram-id
в поле «Telegram-id» из Варианта 1 при заданном `DEV_LOGIN_SECRET` не сработает —
бэкенд ответит `401`, поле там нужно только для Варианта 1 (пустой
`DEV_LOGIN_SECRET`).

## Вариант 3б: тот же demo-вход, но на задеплоенном dev-стенде фронта

Вариант 3 работает только при `npm run dev` — секрет живёт в Node-процессе
dev-сервера. На задеплоенном стенде (например, Railway-сервис `RAILWAY_SERVICE_FRONTEND_DEV`
из `frontend:deploy-dev`, `frontend/.gitlab-ci.yml`) этого процесса нет: там
раздаётся уже собранная статика, и подставлять секрет в запрос некому.

**Осознанный компромисс** (проговорено и принято отдельно от остального demo-режима):
секрет в этом случае встраивается прямо в браузерный бандл и уходит в реальном
запросе — то есть виден любому, кто откроет вкладку DevTools → Network на этом
стенде, и с ним можно напрямую дёргать `reseed-demo-data` и demo-вход в обход
интерфейса. Приемлемо ровно потому, что весь demo-режим и так однократный
временный секрет-костыль (спека 003) — но это осознанный риск, а не то же
самое по строгости, что вариант с `DEV_LOGIN_SECRET` в Варианте 3.

Переменные окружения — задаются на самом Railway-сервисе dev-стенда, а не в
`.env` (в `.env` секрет для этого пути не читается — только `VITE_DEV_LOGIN_SECRET`
из окружения сборки):

```
VITE_MOCK_TELEGRAM=1
VITE_API_BASE_URL=https://api-production-3ead.up.railway.app   # напрямую, прокси Vite тут нет
VITE_DEV_LOGIN_SECRET=<тот же секрет, что DevLogin__Secret на бэкенде>
NODE_ENV=development   # иначе панель разработки и весь dev-код вырежутся, как в настоящем проде
```

Сервис деплоится через `Dockerfile` (не Nixpacks) — **каждая** из этих переменных на Railway
должна быть помечена галкой **«Available at build time»** (Service → Variables), иначе `docker
build` её просто не увидит, сборка молча пройдёт без неё. Плюс `NODE_ENV` и
`VITE_DEV_LOGIN_SECRET` должны быть объявлены в самом `Dockerfile` через `ARG ...` + `ENV
...=$...` до `RUN npm run build` — без этого галка в Railway тоже ничего не даст, Docker
игнорирует build-arg, для которого в Dockerfile нет своего `ARG`. Подробнее и как проверить
результат — `docs/deployment/railway.md`, раздел «Как убедиться, что build-time переменные
доехали».

`NODE_ENV=development` — задокументированный Vite-механизм: `vite build`
(его же запускает `npm run build`) при этом всё равно собирает нормальный бандл,
но оставляет живыми ветки `import.meta.env.DEV` (панель разработки, мок Telegram-окружения),
которые в обычной production-сборке вырезаются целиком.

Плюс на бэкенде (Railway API-сервис) — иначе браузер получит CORS-ошибку раньше,
чем дело дойдёт до 401/200:

```
Cors__AllowedOrigins__1=<origin dev-стенда фронта>
```

Дальше всё как в Варианте 3: пустой браузер (без сохранённого выбора в
`localStorage`) при старте сам подставит первого демо-пользователя
(`990000000001`), а переключиться на другого можно полем «Telegram-id».

## Кто мы в браузере и как сбрасывать

Свой аккаунт задаётся в `.env` (`DEV_USER_ID`, `DEV_USER_NAME`,
`DEV_USER_USERNAME`); id подскажет бот [@userinfobot](https://t.me/userinfobot).

В dev-панели (иконка справа сверху) одно поле — **Telegram-id** — и кнопка
«Войти этим пользователем». Это и есть логин: бэкенд опознаёт человека по id,
имя с юзернеймом у существующего аккаунта берутся из базы. Свои имя и юзернейм
уходят только со своим id — при входе под чужим отправляется один id, как в
настоящем логине Telegram, иначе мы затёрли бы чужой профиль своими значениями.
Выбор живёт в `localStorage`, применяется перезагрузкой: initData собирается
один раз при старте.

Если у аккаунта онбординг уже пройден (`status: active`), вход открывает ленту,
а не анкету. Анкета показывается только когда статус `new`/`onboarding` — то
есть после «Частичного сброса» или у нового пользователя.

Юзернейм — не косметика: бэкенд пишет его в `TelegramUsername` при каждом входе
(`AuthenticateTelegramUserCommandHandler`), и без него открытие контакта в мэтче
отдаёт пустую ссылку.

Аватар в браузере недоступен, и вывести его из юзернейма нельзя: проверено
25.08.2026 — `https://t.me/i/userpic/320/<username>.jpg` отдаёт 404, а `.svg`
отдаёт заглушку с инициалами, которую бэкенд не обработает. Настоящую ссылку
знает только клиент Telegram, поэтому шаг «взять фото из Telegram» проверяется
внутри клиента; в браузере кнопки импорта просто нет, фото загружается файлом.

Панель разработки видна и внутри настоящего Telegram — сбросы нужны и там.
Скрыт в этом случае только выбор пользователя: клиент присылает подписанный
initData реального человека, подменить его нечем.

Ниже две кнопки сброса:

| Кнопка             | Что делает                                                                                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Сброс пользователя | `DELETE /api/onboarding/draft` — черновик, статус в `new` и свои свайпы. Открываешься на шаге 1 анкеты с пустой лентой |
| Полный сброс       | то же плюс удаление всех фото (`DELETE /api/users/me/photos/{id}` по каждому)                                          |

Оговорки:

- Согласие с документами сбросом не снимается (эндпоинта нет), поэтому экран
  приветствия после сброса пропускается — сразу шаг 1. Это скорее правильно:
  согласие — юридический факт, а не тестовое состояние.
- «Частичный сброс» не трогает зорки, фото, интересы, согласие и мэтчи —
  эндпоинтов для этого нет.
- «Полный сброс» удаляет аккаунт насовсем: восстановления в API нет, и повторный
  вход этим же Telegram-id вернёт `410 USER_DELETED`. Чтобы продолжить тестировать,
  впиши другой Telegram-id в поле выше.

## Чего на стенде не хватает

- Origin фронтенда не добавлен в `Cors:AllowedOrigins`. Для разработки это не
  мешает — в dev всё идёт через прокси. Понадобится к первому деплою фронта:
  мини-апп внутри Telegram грузится в iframe с нашего домена, а не с
  `web.telegram.org`, поэтому запросы к API будут кросс-доменными.
