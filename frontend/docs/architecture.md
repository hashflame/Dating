# Архитектура фронтенда

Живой документ. Обновляется, когда меняется структура — не задним числом.

## Слои

| Слой      | Что внутри                                                 | Может импортировать      |
| --------- | ---------------------------------------------------------- | ------------------------ |
| `app`     | точка входа, провайдеры, роутер, глобальные стили          | всё                      |
| `pages`   | экраны: композиция доменов и виджетов, без бизнес-логики   | widgets, domains, shared |
| `widgets` | составные блоки, переиспользуемые между экранами           | widgets, domains, shared |
| `domains` | предметные области: типы, запросы, стейт, UI домена        | domains, shared          |
| `shared`  | UI-кит, http-клиент, конфиг, i18n, Telegram, утилиты, хуки | shared                   |

Слайс = папка внутри слоя. Сегменты внутри слайса: `api/`, `model/`, `types/`, `ui/`, `lib/`.
Наружу слайс отдаёт только `index.ts`.

Направление импортов и публичные API проверяет `eslint-plugin-boundaries`
(конфиг — `eslint.config.js`, секция «Архитектура»). Нарушение = ошибка линта.

## Сегменты shared

| Сегмент    | Что внутри                                                           |
| ---------- | -------------------------------------------------------------------- |
| `api`      | транспорт: `apiRequest`, `ApiError`, `stub`                          |
| `config`   | `env`, константы путей роутов                                        |
| `hooks`    | переиспользуемые хуки; папка появляется с первым хуком               |
| `i18n`     | инстанс i18next, локали ru/be/en                                     |
| `lib`      | чистые утилиты по темам; сейчас только `cn`                          |
| `telegram` | обёртки над Telegram SDK                                             |
| `types`    | типы-утилиты без предметного смысла; папка появляется с первым типом |
| `ui`       | переиспользуемые компоненты; `ui/kit` — примитивы shadcn             |

Компоненты `shared/ui`, собранные по макетам и рассчитанные на остальные секции
(фильтры ленты, интересы, профиль): `Card` (секции и подсказки), `Field`
(подпись + контрол + пояснение), `SegmentedControl` (выбор одного из 2–3 вариантов),
`OptionCard` (крупный вариант с иконкой), `ListRow` (строка списка), `RangeField`
(диапазон чисел с полями и слайдером), `ProgressBar`, `Logo`, `EmptyState`,
`ErrorState`.

Состояния взаимодействия живут в вариантах примитивов shadcn, а не в отдельных
утилитах: у `toggle` есть вариант `surface` (рамка и фон карточки, нейтральное
наведение, фирменное выбранное состояние) и `segment` (сегмент внутри дорожки).
`SegmentedControl` и `OptionCard` задают только размер и типографику — поведение
приходит от примитива.

## Ключевые решения

**Роутер на memory history.** Telegram передаёт launch params в `location.hash`
и управляет навигацией нативной кнопкой «Назад». Браузерная история конфликтует
с этим, поэтому URL не используется как источник состояния навигации.
Deep links приходят через `startParam`, а не через путь.

**Тема приходит от телефона, а не из приложения.** Цепочка: настройка системы →
тема Telegram-клиента → переменные `--tg-theme-*` на `:root` → токены приложения
(`--background`, `--primary`, …). Своей темы у приложения нет, светлая и тёмная
версии не верстаются отдельно. Класс `.dark` и `color-scheme` синхронизируются
по признаку `miniApp.isDark`. Фирменные цвета — отдельный токен `--brand`,
он от темы не зависит.

**Переключатель темы для разработки.** В браузере мок окружения отдаёт параметры
темы по `prefers-color-scheme`, а переключатель в `app/dev/DevThemeToggle.tsx`
позволяет форсировать светлую или тёмную. Он не подменяет тему в обход SDK, а
посылает то же событие `theme_changed`, что и настоящий клиент, — поэтому проверяет
рабочий путь, а не отдельную ветку кода.

**Dev-код отрезается на сборке.** Мок окружения, переключатель темы и мобильная
консоль закрыты проверкой `import.meta.env.DEV`, которую Vite сворачивает в
константу, так что модули выбрасываются из бандла целиком. Проверяется поиском
dev-строк в `dist/assets/*.js` после `npm run build`.

**Плоский слой domains вместо entities + features.** Один домен — одна папка,
без разделения «сущность/фича». Меньше решений о том, куда положить файл.

**Типы живут в двух местах, и это осознанно.** `domains/<домен>/types` — типы
предметной области (`Viewer`, `Match`): они принадлежат домену и меняются вместе
с его запросами. `shared/types` — типы-утилиты без предметного смысла: они про
TypeScript, а не про дейтинг. Общая папка типов быстро превращается в свалку,
которую импортируют все и от которой нельзя отвязать ни один домен.

**Тот же принцип у api.** `shared/api` — транспорт, один на приложение: клиент,
класс ошибки, заглушки. `domains/<домен>/api` — конкретные запросы домена.
Транспорт общий, запросы принадлежат домену.

**Утилиты разбиты по темам, а не свалены в `utils`.** Файл называется по теме
(`cn.ts`, дальше `date.ts`, `number.ts`), и появляется вместе с первым вызовом.
Форматирование дат, чисел и расстояний делает `Intl` с локалью из i18n —
отдельные библиотеки для этого не нужны.

**Правило первого потребителя.** Утилита, хук, тип и компонент создаются вместе
с местом, которое их вызывает. Исключение — обёртки над платформой
(`shared/api`, `shared/telegram`): их задача обратная, не пустить SDK и `fetch`
в остальной код, поэтому они могут существовать заранее.

**Один файл на эндпоинт.** Запрос и его react-query хук лежат вместе
в `domains/<домен>/api/use-<что-то>.ts`; наружу отдаётся только хук. Ключи кэша
переезжают в отдельный файл, когда их использует второй эндпоинт.

**Формы слов по числу — через i18n, а не через свою функцию.** Ключи с суффиксами
`_one/_few/_many` в локалях; `Intl.PluralRules` внутри i18next сам выбирает форму
для русского и белорусского.

**Известное ограничение белорусской локали.** В части движков (проверено в Chromium)
у `Intl` нет данных для `be`: локаль сводится к `ru`, поэтому названия месяцев и
относительное время для белорусского выводятся по-русски. Формы числа при этом
корректны. Если это станет заметно — переводим конкретные места ключами вместо `Intl`.

**Контракт API: конверт и два способа авторизации.** Бэкенд отвечает
`{ data }` на успех и `{ error: { code, message, details, action } }` на ошибку.
Конверт разворачивает `apiRequest` — в доменах его не видно. `message` уже
локализован сервером, его можно показывать пользователю.

Авторизация двухступенчатая: `POST /api/auth/telegram` принимает сырой initData
в заголовке `X-Telegram-InitData` и отдаёт JWT, все остальные запросы идут
с `Authorization: Bearer`. Токен живёт только в памяти (`shared/api/auth-token.ts`):
он короткоживущий и в любой момент переполучается из initData, так что хранить
его в localStorage — риск без выигрыша.

**Dev-прокси вместо CORS.** `/api` в dev проксируется Vite на
`VITE_API_PROXY_TARGET`, поэтому `VITE_API_BASE_URL` пустой и в коде используются
относительные пути. Это не только удобство: реальный API отдаёт CORS-заголовки
только для `https://web.telegram.org`, так что напрямую из браузера к нему
обратиться нельзя, а через прокси запрос идёт с сервера и CORS не участвует.

**Подпись initData для входа из браузера.** `POST /api/auth/telegram` принимает
только initData, подписанный токеном бота (HMAC-SHA256 + свежесть 5 минут).
Постоянного обхода в бэкенде для этого пути нет. Поэтому подпись ставит
dev-сервер: `vite/dev-telegram-auth.ts` подменяет заголовок на пути к прокси,
беря токен из `TELEGRAM_BOT_TOKEN`. Переменная без префикса `VITE_`, значит в
бандл не попадает и в браузер не уходит. Алгоритм — тот же, что в
`backend/scripts/generate-telegram-init-data.js`, то есть бэкенд не ослабляется.

Плагин включается только при `VITE_MOCK_TELEGRAM=1`: внутри настоящего клиента
подмена залогинила бы под dev-аккаунтом вместо реального пользователя.

**Demo-вход по секрету — временный, только для ручного тестирования.**
Отдельно от подписи initData бэкенд умеет (спека 003 в `backend/`, секрет
`DevLogin:Secret` пуст по умолчанию) выдавать JWT для одного из 10
фиксированных демо-аккаунтов по заголовкам `X-Dev-Login-Secret` +
`X-Dev-Login-TelegramId`, без `initData` вообще. На фронте это
`vite/dev-login-auth.ts` + `DevDemoUsers.tsx`: тем же приёмом, что и с токеном
бота, секрет (`DEV_LOGIN_SECRET`) подставляется dev-сервером и в браузер не
уходит. Пока секрет задан, он приоритетнее подписи из предыдущего пункта.
Держать в актуальном состоянии не нужно на длинной дистанции — это костыль на
время, пока нет staging-окружения (см. `docs/real-backend.md`), уберётся вместе
с demo-режимом на бэкенде.

На задеплоенном dev-стенде фронта (не в локальном `npm run dev`) Node-слоя,
который прячет секрет, нет вообще — там `authHeaders()` в `shared/api/http.ts`
сама собирает те же заголовки из `env.devLoginSecret` (`VITE_DEV_LOGIN_SECRET`,
намеренно с префиксом `VITE_`, то есть виден в бандле — компромисс, принятый
только для этого временного стенда, см. Вариант 3б в `docs/real-backend.md`).
Оттуда же берётся дефолтный демо-пользователь на первый заход в пустом браузере
(`DEMO_FALLBACK_USER` в `shared/telegram/dev-user.ts`) — иначе приложение падало
бы на старте раньше, чем можно было открыть панель разработки.

**Один шрифт — Manrope.** В макетах стоят Fraunces и Lato, но у обоих нет
кириллицы (только latin/latin-ext), а интерфейс русско-белорусский. Manrope
подобран как замена: переменный, 200–800, кириллицу рисовал автор шрифта,
держит и заголовок 28px, и подпись 13px. Самохостится через `@fontsource-variable`
(кириллический сабсет — 14.5 kB), внешних запросов к Google Fonts нет.

**Фирменные цвета отдельно от темы.** Семантические токены
(`--background`, `--foreground`, `--card`, …) приходят из темы Telegram.
Цвета идентичности из макетов (`--brand`, `--amber`, `--moss`, `--cornflower`,
`--tag`) от клиента не зависят. Осознанное отклонение от макетов: тёплый фон
`#FBF9F5` не используем — фон берём у клиента, иначе в тёмной теме и в кастомных
темах приложение выглядит чужеродно.

**Ширина ограничена на большом экране.** Мини-апп живёт в узком окне, поэтому
`RootLayout` центрирует содержимое и держит `max-w-[26rem]`. В Telegram Desktop
и в браузере при отладке экран выглядит так же, как на телефоне, — иначе верстка,
рассчитанная на 390px, растягивалась бы на всю ширину монитора.

**Акценты фирменные, поверхности — из темы Telegram.** `--primary` и `--ring`
заведены на `--brand`, а не на синий `button_color`/`accent_text_color` клиента:
иначе синий фокус и синие рамки спорят с красным брендом на одном экране.
`--accent` — нейтральная подсветка при наведении (6% от цвета текста),
`--brand-soft` — мягкая фирменная подложка выбранного состояния. Фон, карточки
и текст по-прежнему берутся у клиента, поэтому приложение остаётся родным.

Следствие: отдельный вариант кнопки `brand` не нужен — `default` и есть фирменная.

**shadcn там, где он даёт поведение.** Интерактивные контролы взяты из shadcn:
`Button`, `Input`, `Checkbox`, `Select`, `Slider`, `ToggleGroup`. Они приносят
состояния `hover`/`focus-visible`/`data-[state=on]`/`disabled`, клавиатуру и роли
доступности — то, что вручную обычно недоделывают.

Наши `SegmentedControl` и `OptionCard` — это `ToggleGroup(Item)` с оформлением из
макетов, поэтому выбор, стрелки клавиатуры и `aria` держит radix, а не наш код.
`SegmentedControl` несёт группу внутри себя и принимает `value`/`onValueChange`.
`OptionCard` — только элемент: он обязан жить внутри `ToggleGroup` (`type="single"`
или `"multiple"`), состояние выбора хранит группа.

**Выпадающие списки ограничены в самом примитиве.** У `SelectContent` задано
`position="popper"` и `max-h-[min(16rem,var(--radix-select-content-available-height))]`:
список из 60+ лет занимает 256 px, а не весь экран. Ограничение живёт в примитиве,
а не в каждом месте вызова.

Единственное сознательное отступление от стокового shadcn: `SelectContent` не
рендерит `SelectScrollUpButton`/`SelectScrollDownButton` — вместо них нативная
прокрутка. Сами компоненты в файле остались и экспортируются, так что вернуть их
можно одной строкой. Причина: в длинном списке они читались как первая и последняя
строка, оформленные иначе, чем остальные.

**Группы переключателей — через проп `spacing`, не через свои радиусы.**
`ToggleGroup` со `spacing={0}` (значение по умолчанию) склеивает элементы
в единую полосу: `rounded-none` плюс `first:rounded-l-md` и `last:rounded-r-md`.
Для сетки карточек и для дорожки сегментов это не подходит — передаём
`spacing={2}` и `spacing={1}` соответственно, и каждый элемент остаётся
самостоятельным. Переопределять радиусы классами бессмысленно: они объявлены
в вариантах `first:`/`last:`, у которых специфичность выше.

Где radix не даёт поведения — не берём его: `ProgressBar` и `Field` собраны
обычной разметкой. Зонтичный пакет `radix-ui` плохо тряхается деревом, и ради
статичной полосы или подписи он тянет лишние килобайты в главный чанк.

**Единственная тяжёлая библиотека держится в ленивом чанке.** `motion` (~100 kB)
нужен только жесту свайпа, поэтому `SwipeDeck` лежит в `pages/feed/ui`, а не
в домене: барель домена импортирует и панель разработки из главного чанка, и
через него motion уезжал в стартовую загрузку. Проверено сборкой: после переноса
главный чанк 371 kB вместо 495 kB.

**Тяжёлые примитивы не реэкспортируются из `shared/ui/index.ts`.** Барель
попадает в главный чанк (его импортируют экраны запуска), и всё, что он
реэкспортирует, уезжает туда же. `toggle-group`, `select`, `slider`, а также
`SegmentedControl`/`OptionCard`/`RangeField` импортируются прямым путём и остаются в чанке
своей страницы. Правило: в барель попадает то, что нужно экранам запуска.

По той же причине обвязка шагов онбординга (`OnboardingStep`, `StepDots`,
`BirthDatePicker`) лежит в `pages/onboarding/ui`, а не в домене: барель домена
импортирует экран приветствия из главного чанка, и вся UI-обвязка уезжала бы
вместе с ним. В домене остались только api, model и типы.

**Многошаговая анкета — один слайс страниц.** Пять шагов онбординга живут
в `pages/onboarding` как пять компонентов одного слайса: это один поток с общим
каркасом (`OnboardingStep`), и разносить его по пяти слайсам значило бы плодить
одинаковые `index.ts`. Каждый шаг сохраняется отдельным запросом, состояние
хранит сервер (черновик), а не клиент.

**Черновик подставляется через ожидание загрузки, а не эффектом.** Страница шага
ждёт черновик и только потом рендерит форму, передав данные как `defaultValues`.
Синхронизация `useEffect` + `setState` даёт лишние рендеры и мигание — так делать
не нужно, если можно просто отложить создание формы.

**Онбординг вынесен в отдельный чанк.** `lazyRouteComponent` в `route-tree.ts`:
поток проходят один раз, и формы с radix-примитивами не должны лежать в бандле
вернувшегося пользователя. Основной чанк — 560 kB, онбординг — 148 kB.

**Стартовый экран решает по статусу и согласию, а не по догадкам.** Статусы
`new` и `onboarding` означают «анкета не пройдена» (во второй бэкенд переводит
при сохранении первого шага), остальные ведут в ленту. Внутри анкеты порядок
такой: нет согласия — приветствие, иначе первый незаполненный шаг из
`draft.step`. Согласие берётся из `GET /api/users/me/consent`, поэтому старый
трюк «считать согласие по номеру шага» больше не нужен.

**Заглушки вместо ожидания бэкенда, но без падений.** Нереализованные эндпоинты
закрываются `stub()` и фиксируются в `docs/api-gaps.md`. Если экран может жить
без данных — отсутствие эндпоинта не должно его ломать: `useViewer` в production
отдаёт `null`, и зависящий блок просто не рисуется. `stub()` при этом остаётся
только в dev, чтобы видеть вёрстку.

## Границы приложения

- Единственная точка обращения к API — `apiRequest` из `@/shared/api`.
- Единственная точка работы с Telegram — `@/shared/telegram`.
- Единственная точка чтения окружения — `@/shared/config/env.ts`.
- Переиспользуемые компоненты — `@/shared/ui`, хуки — `@/shared/hooks`,
  утилиты — `@/shared/lib`. Дубликаты и код без потребителя не проходят ревью.
- Папка `backend/` — только для чтения контракта API.
