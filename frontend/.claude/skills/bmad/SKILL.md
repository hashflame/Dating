# BMAD — процесс разработки

Идея: не пытаться сделать всё в одном большом запуске, а разбить работу на роли
с чёткими входами и выходами. Каждая роль оставляет артефакт в `frontend/docs/`,
следующая роль читает его и не нуждается в истории переписки.

## Роли и артефакты

| Роль         | Скилл            | Вход              | Выход                                     |
| ------------ | ---------------- | ----------------- | ----------------------------------------- |
| Аналитик     | `bmad-analyst`   | идея от человека  | раздел брифа в `docs/prd.md`              |
| Продакт      | `bmad-pm`        | бриф              | эпики и список историй в `docs/prd.md`    |
| Архитектор   | `bmad-architect` | PRD               | `docs/architecture.md`, `docs/ux-spec.md` |
| Скрам-мастер | `bmad-sm`        | PRD + архитектура | файл истории в `docs/stories/`            |
| Разработчик  | `bmad-dev`       | одна история      | код + отчёт в файле истории               |
| QA           | `bmad-qa`        | история + код     | вердикт в файле истории                   |

## Две фазы

**Фаза планирования** — один раз на эпик:

```
bmad-analyst → bmad-pm → bmad-architect
```

**Цикл разработки** — повторяется на каждую историю:

```
bmad-sm → [человек одобряет] → bmad-dev → bmad-qa → следующая история
```

## С чего начать

| Ситуация                                              | Роль                                  |
| ----------------------------------------------------- | ------------------------------------- |
| Есть только идея, непонятен объём                     | `bmad-analyst`                        |
| Понятно, что делаем, нужно разбить на эпики и истории | `bmad-pm`                             |
| Истории есть, непонятно как устроить технически       | `bmad-architect`                      |
| План есть, нужна следующая задача в работу            | `bmad-sm`                             |
| Есть одобренная история — писать код                  | `bmad-dev`                            |
| Код написан, нужна проверка                           | `bmad-qa`                             |
| Мелкая правка, багфикс, рефакторинг                   | без BMAD, сразу код + `fe-done-check` |

BMAD нужен для новой функциональности. Для правки текста, цвета или бага он лишний.

## Как формулировать запрос

Скиллы подхватываются автоматически по смыслу запроса — называть их не обязательно.
Достаточно сказать, что делаем и на каком шаге находимся.

### Полный цикл новой страницы, с нуля

Шаг 1 — понять, что делаем:

```
Хочу экран «Мои симпатии»: пользователь видит, кто его лайкнул, и может ответить.
Разберись, что именно нам нужно, и составь бриф.
```

Шаг 2 — разбить на задачи:

```
Бриф согласован. Разбей на истории с критериями приёмки и задай порядок.
```

Шаг 3 — спроектировать:

```
Истории готовы. Спроектируй техническое решение: какие домены и файлы,
откуда данные, что в кэше, какие состояния экрана. Контракт сверь с backend/.
```

Шаг 4 — подготовить задачу:

```
Подготовь первую историю к работе.
```

Шаг 5 — писать код (по одной истории за запуск, лучше в новом чате):

```
Возьми историю 3.1 и реализуй её.
```

Шаг 6 — проверить:

```
Проверь историю 3.1.
```

### Короткий путь, когда решение уже понятно

```
Добавь экран «Мои симпатии» по адресу /likes: список тех, кто меня лайкнул,
аватар + имя + возраст, кнопки «Ответить» и «Пропустить».
Данные возьми из backend/, чего нет — заглушкой. Состояния загрузки, пусто и ошибки обязательны.
```

Этого хватает: слои, стили, локализацию, кэш и заглушки агент возьмёт из скиллов сам.

### Что стоит указывать в запросе

- Что видит и делает пользователь — вместо перечисления файлов.
- Путь роута, если он важен.
- Откуда данные, если знаешь; иначе «сверься с backend/».
- Крайние случаи: пустой список, ошибка, лимит, оплата.
- Что не делать в этой задаче.

### Чего указывать не надо

- «Используй Tailwind / react-query / FSD / скилл fe-styles» — это уже в правилах.
- Названия компонентов, хуков и папок — их выберет архитектура.
- «Не забудь про типы, локализацию и проверку линтером» — входит в обязательный чеклист.

## Правила процесса

1. **Одна история — один запуск.** История должна быть самодостаточной: разработчик
   читает только её и скиллы, а не всю переписку.
2. **Человек одобряет истории.** `bmad-sm` создаёт историю в статусе `draft`.
   В работу берётся только `approved`.
3. **Роль не делает работу следующей роли.** Продакт не проектирует папки,
   архитектор не пишет код, разработчик не переписывает критерии приёмки.
4. **Артефакты обновляются, а не дописываются заново.** `docs/architecture.md` — живой
   документ, а не протокол.
5. **Не хватило информации — остановись и спроси.** Догадка, зафиксированная
   в документе, дорого стоит на следующих шагах.

## Где что лежит

```
frontend/docs/
  prd.md            что делаем и зачем: бриф, эпики, истории
  architecture.md   как это устроено технически
  ux-spec.md        экраны, навигация, состояния
  api-gaps.md       чего не хватает от API
  stories/          истории; TEMPLATE.md — шаблон
```

Правила написания кода лежат отдельно, в скиллах `fe-*`. BMAD отвечает за процесс,
`fe-*` — за код.
