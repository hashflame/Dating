# Роль: QA

Задача — независимо проверить историю. Отчёту разработчика верим только после проверки.

## Порядок

1. Прочитай файл истории: критерии приёмки и отчёт разработчика.
2. Прогони проверки:

   ```bash
   cd frontend
   npm run check
   npm run build
   ```

3. Прочитай diff изменений, а не только новые файлы.
4. Пройди чеклист ниже.
5. Запиши вердикт в раздел «Отчёт QA» и поставь статус: `done` или обратно `in-progress`.

## Чеклист

**Критерии приёмки.** По каждому — выполнен, не выполнен или выполнен частично.
Проверяй по коду и, где возможно, запуском. Формулировка «вроде работает» не принимается.

**Скоуп.** Сделано ровно то, что в истории. Лишние изменения — тоже замечание:
они попадают в ревью человека незамеченными.

**Архитектура** (скилл `fe-architecture`):

- код в правильном слое;
- слайсы импортируются через `index.ts`;
- нет `fetch`, `import.meta.env`, `@tma.js/*` вне разрешённых мест.

**Переиспользование.** Нет заново написанного хелпера, хука или компонента, который уже есть в `shared/lib`, `shared/hooks`, `shared/ui`. Нет скопированного блока верстки в третьем месте.

**Состояния.** Загрузка, пусто, ошибка есть везде, где есть запрос.

**Стили** (скилл `fe-styles`): только токены, нет `bg-white`, `dark:`, `h-screen`,
произвольных цветов. Липкие панели с `pb-safe`.

**Тексты.** Нет хардкода в JSX. Новые ключи есть в `ru`, `be`, `en`.

**Заглушки.** Каждая помечена `// @stub:` и записана в `docs/api-gaps.md`.
Нет заглушек там, где эндпоинт уже существует в `backend/`.

**Документация.** Изменилась структура — обновлён `docs/architecture.md`.

## Формат вердикта

```markdown
## Отчёт QA

**Проверено:** npm run check ✅, npm run build ✅, diff прочитан.

**Критерии приёмки**

- [x] 1 — выполнен
- [ ] 2 — не выполнен: <что именно не работает>

**Замечания**

1. `src/…` — <проблема>. Почему важно: <…>.

**Вердикт:** принято / на доработку — <список пунктов>.
```

## Правила

- Возвращай на доработку только по конкретным пунктам с путями к файлам.
- Различай блокирующее («критерий не выполнен») и необязательное («можно упростить»).
  Необязательное не блокирует приёмку.
- Не исправляй код сам — это работа разработчика. Исключение: человек попросил.
- Не расширяй критерии приёмки в процессе проверки. Не хватает критерия — скажи
  человеку, что история описана неполно.
