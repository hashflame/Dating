# Spec 003: Демо-данные для ручного тестирования на prod

**Status:** Approved (2026-08-25)
**Date:** 2026-08-25

## Problem

Фронтендер тестирует Telegram Mini App вручную и не может нормально проверить ленту, мэтчи,
лайки и профиль — единственное развёрнутое окружение (Railway, `production`, см.
`docs/deployment/railway.md`) содержит только справочники (города/интересы/предпочтения), но ни
одного пользователя. Дополнительно фронтендер хочет тестировать в обычном браузере, а не только
внутри Telegram — а обычная аутентификация (T-1.1) требует валидный Telegram WebApp `initData`,
которого в браузере нет.

Нужны два связанных куска:
1. Набор демо-пользователей с анкетами, фото, связями (мэтчи/лайки) — то, что видно в UI.
2. Способ получить JWT для одного из демо-пользователей без реального Telegram — то, чем в это UI
   попасть.

## Scope

### In
- 10 фиксированных демо-пользователей с полными анкетами (фото, интересы, био и т.д.).
- Связи между ними: часть — взаимные мэтчи (для экранов мэтчей/хаба/архивации), часть —
  однонаправленные лайки (для экрана списков лайков).
- `POST /api/dev/reseed-demo-data` — идемпотентный endpoint, полностью пересоздающий эти 10
  пользователей и их связи по запросу.
- Расширение `POST /api/auth/telegram`: dev-режим, который по секрету и `TelegramId` выдаёт JWT
  для одного из 10 демо-пользователей в обход проверки `initData`.
- Конфигурация `DevLogin:Secret` — пустая по умолчанию (обе фичи выключены, пока секрет явно не
  задан на Railway).

### Out
- Полноценная demo/staging-среда, отдельная от prod (переиспользуем текущее единственное
  окружение, см. `docs/deployment/railway.md` — «одно окружение, без staging»).
- Флаг изоляции демо-данных (`IsSeed` и т.п.) и фильтрация их из «настоящих» списков — по вашему
  решению, зачистка вручную, когда понадобится.
- Возможность dev-логина под любым `TelegramId` (не только под 10 демо) — сознательно не делаем,
  см. Domain Model.
- Данные для фич вне текущего скоупа фронтенд-тестирования: кошелёк/история зорок (T-8.1),
  вопрос дня, миниигра, доска идей, разные города (все 10 — в одном городе, Минск).
- Реальная загрузка фото через полный pipeline модерации (T-3.2, POST-MVP, не реализован).

## Domain Model

**Идентификация демо-пользователей.** Фиксированный, детерминированный набор — не создаётся
заново со случайными Id при каждом пересидировании:
- `TelegramId`: зарезервированный блок `990000000001`–`990000000010` (заведомо вне диапазона
  настоящих Telegram-id, чтобы не столкнуться с реальным пользователем).
- `Id` (Guid): литеральные детерминированные GUID той же схемы, что `CitySeed`/`InterestSeed`
  (`00000000-0000-0000-0aXX-...`), новый префикс для демо-пользователей.

**Анкеты.** 10 пользователей, все в Минске (`CityId` = seed-город "Минск"), разный пол
(5 `Male` / 5 `Female`), возраст 20–35, разные `DatingGoal`, заполненные `Bio`,
`ProfileCompleteness = 100`, `Status = Active`, `SparksBalance = 100` (без этого открытие
контакта/суперлайк/разблокировка лайков падают с `INSUFFICIENT_SPARKS` на пустом балансе — сама
история зорок по-прежнему вне скоупа, баланс проставляется напрямую, без `SparkTransaction`), у
каждого задан `TelegramUsername`
(`demo_user_1`…`demo_user_10`) — чтобы можно было проверить экран открытия контакта (T-7.3). У
каждого — 2–3 фото (одно `IsMain = true`), сгенерированных как плейсхолдеры и загруженных через
существующий пайплайн (`IPhotoStorageService`/обработка изображений из T-3.1), чтобы `Url`/
`ThumbnailUrl`/`MediumUrl` были такими же по форме, как у настоящих фото, и лежали на
`Storage__PublicBaseUrl` (реальный MinIO). Плюс 3–5 интересов на пользователя из существующего
`InterestSeed`.

**Связи.**
- Мэтчи: 4 взаимные пары среди 10 (роли `User1Id`/`User2Id` канонизированы по правилу из
  `Match.cs`), `Status = Active`, `MatchedAt` в прошлом. Один из 4 мэтчей — с `ContactUnlockedAt`
  проставленным (для проверки уже открытого контакта), один — с `ArchivedAt`/`ArchivedReason`
  (для проверки архива, T-7.4).
- Лайки: несколько однонаправленных `Swipe` с `Type = Like` от/к пользователям вне мэтчнутых пар
  (для входящих/исходящих списков, T-6.1) — не приводящие к мэтчу (обратной записи нет).
- Остальные 2 пользователя без связей — просто видны в ленте.

**Пересидирование** (`POST /api/dev/reseed-demo-data`) — снести и создать заново: удаляются
именно эти 10 `TelegramId` и все их `Photo`/`UserInterest`/`Swipe`/`Match` (по `User1Id`/`User2Id`
или `FromUserId`/`ToUserId`), затем всё создаётся заново с тем же детерминированным набором
Id/`TelegramId`/`TelegramUsername`. **Важный риск, принятый осознанно** (см. Deferred Decisions):
если к этому моменту уже есть настоящий Telegram-пользователь, у которого лайк/мэтч с одним из
демо-аккаунтов, — пересидирование удалит и его сторону этой связи. Сейчас это допустимо, так как
на проде ещё нет реального трафика.

**Dev-логин** — расширение `POST /api/auth/telegram` в `TelegramAuthMiddleware`
(`src/Blizka.Api/Auth/TelegramAuthMiddleware.cs`), а не отдельный endpoint: до чтения заголовка
`X-Telegram-InitData` middleware проверяет `X-Dev-Login-Secret` и `X-Dev-Login-TelegramId`.
- Секрет из конфига `DevLogin:Secret` пуст (дефолт) → dev-заголовки полностью игнорируются, ничего
  не меняется в текущей логике.
- Секрет задан, `X-Dev-Login-Secret` совпадает, `X-Dev-Login-TelegramId` — один из 10 демо
  (`990000000001`–`990000000010`) → проверка `initData` пропускается целиком, в
  `HttpContext.Items[ItemsKey]` кладётся синтетический `TelegramInitData` для этого
  `TelegramId`/`FirstName`/`Username` (взятые из демо-анкеты), запрос идёт в `AuthController`
  как обычно → обычный JWT.
- Секрет задан, `X-Dev-Login-Secret` присутствует, но неверен → `401` сразу (fail closed, не
  утекает в обычную ветку).
- Секрет задан и верен, но `X-Dev-Login-TelegramId` не входит в 10 демо (либо отсутствует) →
  `401` — через этот обход нельзя создать/зайти под произвольным аккаунтом.

## API Contract

| Метод | Путь | Тело/заголовки | Ответ | Ошибки |
|---|---|---|---|---|
| `POST` | `/api/auth/telegram` (существующий, расширяется) | Заголовки `X-Dev-Login-Secret` + `X-Dev-Login-TelegramId` — опциональная альтернатива `X-Telegram-InitData` | `200 ApiResponse<AuthTelegramResponse>` — тот же контракт, что у обычного логина | `401` — неверный секрет, либо `TelegramId` не из 10 демо, либо (как и раньше) отсутствует/невалиден `initData`, когда dev-заголовки не переданы |
| `POST` | `/api/dev/reseed-demo-data` | Заголовок `X-Dev-Login-Secret` (тот же секрет, что у dev-логина) | `200 ApiResponse<ReseedDemoDataResponse>` — список из 10 `{ telegramId, name, isMain photo url }`, чтобы фронтендер видел, под кого логиниться | `401` — если `DevLogin:Secret` не задан на сервере, либо переданный секрет неверен/отсутствует |

`AllowAnonymous` на обоих путях (как и на текущем `/api/auth/telegram`) — доступ регулируется
секретом, не JWT.

## Authorization

Обе фичи защищены единственным общим секретом `DevLogin:Secret` (env `DevLogin__Secret` на
Railway), который:
- пуст по умолчанию → обе фичи выключены;
- задаётся вами вручную на Railway, когда нужно дать доступ фронтендеру;
- не привязан к ролям/пользователям — это не полноценная авторизация, а «дверь для одного
  доверенного человека», сознательно упрощённая по вашему запросу.

## Edge Cases & Failure Modes

- **`DevLogin:Secret` не задан** — оба endpoint'а ведут себя как будто dev-фич не существует
  (`X-Dev-Login-*` заголовки игнорируются на логине; reseed отвечает `401`).
- **Повторный вызов `reseed-demo-data` подряд** — идемпотентен: очищает и создаёт заново тот же
  результат, ошибок не возникает даже если предыдущий вызов только что отработал.
- **Реальный пользователь успел лайкнуть/смэтчиться с демо-аккаунтом до пересидирования** — его
  сторона связи удаляется вместе с демо-пользователем (см. Domain Model, риск принят).
- **Фронтендер залогинен как демо-пользователь A, затем вызывают reseed** — токен A остаётся
  формально валидным (JWT не привязан к живой сессии), но `UserId` внутри токена теперь
  указывает на свежепересозданную (другую по данным, тот же `Id`) запись — фронтендеру нужно
  перелогиниться после пересидирования, если менялись данные конкретно этого пользователя.
- **Секрет передан, но `X-Dev-Login-TelegramId` не число / не входит в 10 демо** — `401`, никаких
  побочных эффектов (пользователь не создаётся).

## Non-Functional Requirements

- Объём тривиальный (10 пользователей, ~25 фото, ~10 связей) — время выполнения
  `reseed-demo-data` некритично, синхронный HTTP-запрос без фоновой очереди.
- Секрет передаётся только в заголовках (не в query/URL), чтобы не оседал в логах прокси/браузера.

## Integrations

- Фото демо-анкет реально загружаются в MinIO через существующий `IPhotoStorageService`
  (тот же прод-бакет `blizka-photos`), никаких новых внешних сервисов.
- Telegram Bot API не участвует — dev-логин полностью обходит Telegram.

## Acceptance Criteria

- **AC-1**: При пустом (не заданном) `DevLogin:Secret` вызов `POST /api/dev/reseed-demo-data` с
  любым заголовком `X-Dev-Login-Secret` возвращает `401`, БД не меняется.
- **AC-2**: При заданном `DevLogin:Secret` и верном заголовке `POST /api/dev/reseed-demo-data`
  создаёт ровно 10 пользователей с `TelegramId` в диапазоне `990000000001`–`990000000010`, у
  каждого — анкета, 2–3 фото, 3–5 интересов; отвечает `200` со списком demo-аккаунтов.
- **AC-3**: Среди 10 демо — ровно 4 взаимных `Match` (`Status = Active`), из них один с
  проставленным `ContactUnlockedAt`, один — с `Status = Archived`/`ArchivedReason`; и есть хотя бы
  один однонаправленный `Swipe(Type=Like)` без ответного мэтча.
- **AC-4**: Повторный вызов `POST /api/dev/reseed-demo-data` не создаёт дублей — в БД по-прежнему
  ровно 10 демо-пользователей с теми же `TelegramId`/`Id`, старые фото/мэтчи/лайки заменены новыми.
- **AC-5**: `POST /api/auth/telegram` с верным `X-Dev-Login-Secret` и `X-Dev-Login-TelegramId`,
  равным одному из 10 демо, возвращает `200` с тем же форматом ответа, что обычный Telegram-логин
  (`AuthTelegramResponse`), и валидный JWT для этого пользователя.
- **AC-6**: `POST /api/auth/telegram` с верным секретом, но `X-Dev-Login-TelegramId`, не входящим
  в 10 демо, возвращает `401`, пользователь не создаётся.
- **AC-7**: `POST /api/auth/telegram` с неверным `X-Dev-Login-Secret` возвращает `401`
  немедленно, не проверяя `X-Telegram-InitData`.
- **AC-8**: `POST /api/auth/telegram` без dev-заголовков продолжает работать по-старому (реальный
  `initData`) — расширение не ломает существующий T-1.1 флоу.

## Deferred Decisions

- **Изоляция демо-данных от реальных** — решено не делать (флаг `IsSeed`, фильтрация из списков).
  Фолбэк: демо-пользователи зачищаются вручную, когда потребуется. Триггер к пересмотру: как
  только на проде появится реальный трафик, из-за которого демо-профили в ленте/поиске станут
  проблемой для настоящих пользователей.
- **Пересидирование может оборвать связи реальных пользователей с демо-аккаунтами** — решено
  принять риск сейчас. Триггер к пересмотру: то же самое — появление реального трафика.
- **Секрет dev-логина не привязан к ролям/IP/времени действия** — решено оставить максимально
  простым (один секрет в заголовке). Триггер к пересмотру: если понадобится делиться доступом с
  кем-то ещё, кроме одного фронтендера, стоит сменить на более гранулярную схему.
